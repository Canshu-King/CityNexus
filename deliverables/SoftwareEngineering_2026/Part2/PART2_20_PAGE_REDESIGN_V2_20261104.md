These dimensions are orthogonal: an original BL requirement may lack implementation evidence; an EXT may be technically demonstrated in a sandbox but not accepted into product.

## C. Decisions that protect grades and historical truth

1. **Original booking/payment scope remains visible.** FR-029..038 are authentic early baseline. They may be marked `verification pending / not in selected demo` based on real evidence; do NOT claim they were post-baseline or silently delete them.
2. **Original events/replanning remain visible.** FR-039..053 and UC-09/10 were present on 9/4, so calling all autonomous recovery a novel postbaseline feature would be false. Novelty is the continuous operator/group/real-session experience on later branches.
3. **Agency nuance:** source baseline requires explicit acceptance for *major* changes; later Agent runtime may authorise bounded low-risk actions under prior user policy. Avoid the over-simple diagrams saying AI can **never** perform a write or *all* changes require click. The immutable server business-fact gate matters.
4. **Product truth ≠ requirements truth ≠ test truth:** a requirement in YAML is not proof of implementation. An isolated Revolution R108 controlled signed GO flow with self-reported arrival is not live physical presence. An early external route result is not blanket nationwide provider support. A screenshot is not stable release integration.
5. **Course Plan snapshot ≠ actual progress today.** The 65-row plan's percentages and 11 stage costs originate in dated 2026-10-22 material. A fresh independently verified completion census could be shown as a *second* timestamped report, not silently overwrite the frozen Project source. 
6. **Course contract dates ≠ Project task finish.** M12/M13 planned Oct-23 target versus hard Part2 Nov-06 cutoff. Part1 Moodle submission/unaccepted teacher requirement still must not be asserted as verified.
7. **The 20-page PDF is self-contained**. A teacher must be able to see tasks, relationships, resources and costs **inside the PDF** without opening .mpp; GitHub links are evidence supplements only. Private GitHub repos may not be accessible to the marker.
8. **Avoid claiming all 138 have been fully implemented.** Put summary acceptance and source IDs in report; original full 138 `requirements.yaml` plus 138 acceptance oracles and use cases remain immutable reference for audits. If course expects verbatim detailed 138, at 20 pages this conflicts with readability; seek teacher guidance rather than fake completeness.
9. **The user retains control:** the document reports later features and evidence quality honestly and does not silently change requirements version or approve a customer baseline.
