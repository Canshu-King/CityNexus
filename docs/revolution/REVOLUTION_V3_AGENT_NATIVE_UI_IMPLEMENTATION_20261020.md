## 1. 产品硬标准
**让人先看想去的地方、理解行程、自然与 Agent 交流，然后才展开技术细节。**

- 一个可恢复的 Journey 产品上下文、三个一级导航：`探索 / 我的旅程 / 我的`。地图、日程、Agent 工作轨迹是内部视图，不再增加五个底部入口。
- Agent 是全局操作层，底部**唯一聊天输入**适配地图、日程、景点详情、执行、Guardian 与多人协作。打开工作详情不会重新创建 GoalTask，连续上下文必须保持签名 traveler、journey_id、task_id。执行期可以有独立合法的 AgentRun，但产品上表现为同一个旅行伙伴，不能伪造底层同一任务。
- 默认突出真实旅行内容：地点照片、地图、方案、每日行程、下一站；工具细节折叠可查。Agent 做研究/提议应让成果出现在原地，不迫使用户跳到聊天专页。
- Agent 主动利用已获授权的工具和数据，不因个别 provider 缺字段而整体罢工；未知状态清楚标注，不虚构开放、门票、路程、预约或已到达。

## 2. 十张 UI 的操作合同（十个场景，并非十个孤立 SPA）
| 场景 | 用户唯一主动作 | 点击后真正发生的事 |
|---|---|---|
| 01 探索首页 | 说一句旅行意图或恢复当前旅行 | 无旧 Journey 可建草案；有 Journey 优先展示现阶段旅程与 Agent 上一步结果；首次偏好可在对话补齐 |
| 02 Agent 研究 | 继续聊、选 `ask_traveler` 选项、看工作详情 | 延续同一任务；`DISCUSS` 先讨论、用户明确研究意图后开始工具研究；实时事件驱动状态；研究地点/媒体/草案就地可见 |
| 03 地图探索 | 点图钉、筛选或查看路线 | 选中与日程/地点图库共同的 candidate_id；点选状态跨视图同步；示意坐标/底图区分真实道路导航 |
| 04 地点详情 | 看来源照片、查看营业/票价、加入当前行程 | 提示签名地点来源、作者/许可与更新时间；加入后立即联动地图和草案，不把估算变核实 |
| 05 三方案对比 | 切 A/B/C、比较人均费用/节奏/来源、选一个 | 三方案显示独立内容；选用 current draft variant 并生成统一可编辑的当前日程，页面不用让用户重新手动找地点 |
| 06 每日日程 | 切 Day1/Day2、改 slot 或和 Agent 说「第二天下午轻松点」 | 同一 task 局部替换，地图、图片、费用同步，刷新读回同一版本；让 Agent 修改不是新建并行 Journey |
| 07 出发准备 | 处理待办、确认出发 | 已选草案到正式 PlanVersion 的可理解桥接；展示「已核实/AI估算/待办理」；酒店被推荐不等于已预订；办理失败不消失 |
| 08 旅行中 | 看下一站、打开导航、本人确认到达 | 由真实执行态和有效路线读取进度；未经用户确认/真实定位证据不可显示已到达 |
| 09 Guardian 应变 | 看有出处的影响、对比备选、提议修改 | 真实 event 与模拟 fixture 严格区分；预算差和预计时间可对比；**产生 proposal，不直接覆盖 active shared PlanVersion** |
| 10 多人决策 | 讨论、本人确认/拒绝并查看状态 | 依据服务器成员绑定权限和旅程既定决策规则变更；示例 2/3 是待确认，发起人不可替另一成员点击 |

`我的` 独立导航仍需可用的偏好、历史、最近旅行、身份/授权入口，虽然 V3 概念图没有单独做第 11 张。

## 3. 状态与数据归一规则

一条可解释的用户旅程：目标 / 讨论 → 研究 → 已有可编辑方案 → 已选当前方案 → 出发准备 → 正式执行 → 已完成。Guardian 事件、提议与多人确认是执行或准备中的**并行分支**，未被采纳时原计划继续存在。

真实来源数据必须由后端真相映射到单一 UI 字段：地点 identity、坐标与 coordinate_system、媒体来源/许可、营业、门票、路线 provider、获取时间与来源级别、成员权限；地图/照片/行程不能分别显示冲突数值。

### 固定的演示叙事（仅设计/fixture，不是实时事实）
- 旅行：福建连城，2026-10-24（六）至 2026-10-25（日），2 天 1 晚。
- 成员：我、阿杰、小雨 3 人；预算每人 ¥500，非三人总预算。
- 方案 B 自然轻松人均估算 ¥470；A ¥520（超预算），C ¥495。
- 酒店仅推荐未预订；真实景点营业/门票未知要明确标注「待核实」，不能硬写「已确认」。
- Guardian 演示采用明确标签的**模拟**石门湖暂停开放：替代培田古村预计仍 ¥470/人；替代天一温泉预计 ¥550/人（超 ¥50）。此 fixture 不许出现在真实生产事故卡里。
- 共享提案 2/3 同意、小雨待确认；在示例约定需全员同意时，不可变更 active plan，也不能让当前 traveler 代替小雨确认。

## 4. 分阶段直接实施（以用户可见能力排序）

### Codex P0-A：固定三导航与全局 Agent（先交一个能用的闭环）
1. 从现有 PR #23 组件改造，不另建空白 V3 dashboard。根据 Journey 状态让首次/草案/ACTIVE 的首页分别突出：一句话入口/已有草案/下一站与事件。
2. 手机 390/430 只有一个主工作面板；桌面 1366/1566 可并排地图和日程。保留一处 chat dock，键盘弹起、滚动和页面切换都不遮主 CTA。
3. 当前页有 contextual prompt：例如在地图上说「找水景」，在日程里说「下午别太赶」；任意视图可打开同 task 工作过程。
4. 对话以 PR #23 真实 `DISCUSS` 能力为基线，展示真实 `ask_traveler` 选项与研究操作，不强制用户逐项调模型轮数；是否继续研究需与用户显式意图/已授权能力一致。

### Codex P0-B：地点 → 地图 → 三方案 → 日程 → 正式旅行
1. 写统一 `PlaceProjection`/selection state 或复用既有对应模型，让图库、图钉、日程 slot 共享 provider/source candidate 身份。
2. A/B/C 三方案真正切换、独立费用/景点/节奏与推荐依据；切换后可以查看对应日程，选择方案无额外从头采集地点。
3. 保持同 GoalTask 的局部变更，刷新和重新打开都恢复所选方案及修改历史。
4. 打通 DraftGoalArtifact / selected variant 到正式 PlanVersion / start Journey，后端可分阶段但用户只看一次可追踪的「准备出发」；每个未办事项提供继续行动，不制造死按钮。

### Codex P0-C + Qoder contract：Guardian 与 collective 真闭环
1. Agent 在已授权/真实事件条件下主动发现影响，展示来源及时间戳，提出至少两种替代方案及预算/路线差异。
2. 单人合法更新与多人 shared update 分开：多人创建 proposal → member-bound 本人确认 → 规则达成才正式写入 PlanVersion。若 2/3 不满足则保持未生效。
3. Qoder 负责具名补齐缺失的签名成员读取、源事实归一、正式方案投影/事件与确认端点；优先复用已存在的 Revolution 域模型和 server authority，不要凭前端显示拼出假权限。

## 5. 一次真实人类演示必须跑通的链路
1. 手机无旅程用户直接输一句旅行愿望，进入真实讨论/研究（记录 Journey + GoalTask 身份）。
2. Agent 查真实地点 + 来源照片（连城 + 非连城回归可重用已取得的广州塔证据），用户在地图点选、进详情、加进日程。
3. 真正切换 A/B/C、选 B、看到 Day1/Day2；同 task 一句修改**第二天下午**并刷新，其他 slot 保持不变。
4. 继续到准备出发：只允许展示真实已经核实的项。对未知酒店/票价给明确处理方向；如正式 plan/route provider 不可用就记录可理解的真实 BLOCKED，不改写为成功。
5. 在实际支持的执行环境里进入 ACTIVE，下一站正确；Guardian 如使用模拟数据必须显眼标 fixture，且不启动真实 ProviderCall 冒充官方公告。
6. 在多人情景里记录 2/3 与 3/3，验证 2/3 不修改共享 PlanVersion、3/3 再按既有规则生效。
7. 使用安装版浏览器 390×844、430×932、1366×980、1566×980；证明没有整页溢出、输入被遮、回页丢 task，且主动作没有不可达死路。**最终真人手机亲手操作单列 `USER_VERIFIED=PENDING`，直到用户实际确认。**
