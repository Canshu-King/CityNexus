# CityNexus Revolution V3：10 张独立 UI 的产品架构与操作规则

> **设计参考，不是现有产品功能完成证明。** 10 张 PNG 为静态高保真概念图；照片、地图路线、酒店、价格、事件、天气、交通时间、评价等均为示意，未经实时验证。HTML 页面用于浏览布局和主要跳转，不能替代真实 Agent、provider、授权或手机验收。

## 1. 核心原则

**一个 Journey、一个持续的 Agent 上下文、三个一级导航。** 用户最先看到想去的世界，通过自然语言提出愿望；Agent 把研究成果直接写回地图、地点、方案和日程；详细技术动作按需展开，不让用户学习模型接口或后端状态机。

- **探索**：目的地灵感、真实地点与媒体、地图、地点详情、Agent 研究成果。用户从一句话开始，不预先填完所有表单。
- **我的旅程**：同一 Journey 中的备选方案、当前日程、出发检查、执行、Guardian 应变、同行决策和旅行回顾。
- **我的**：身份、偏好、历史、收藏、提醒、隐私及工具授权。十页并未单独为「我的」设计完整页面，应由产品线补充。
- **Agent**：不是第四个主页面，而是三主空间共享的底部聊天入口、任务动态卡及可展开的工作轨迹。打开独立工作台只为看详细进度和来源，不能导致 task_id 重建。

## 2. 十张 UI 的真实用户动作

| 顺序 | UI | 用户主动作 | 需要发生的产品变化 | 不该发生的事情 |
|---|---|---|---|---|
| 01 | 探索首页 | 用一句话提出旅行目标 | 新建或恢复当前 Journey；Agent 研究任务进入工作状态 | 强迫用户先逐字段填大量表单 |
| 02 | Agent 主动研究 | 随时继续聊天、查看任务进展 | 写入有来源地点、照片、路程和草案；同步探索空间 | 只播放假的进度条、把每次继续聊天当新任务 |
| 03 | 地图探索 | 点地图候选、筛选、加入日程 | 同一地点 ID 驱动地点详情和日程，已选状态同步 | 用画出的示意线冒充真实道路导航 |
| 04 | 地点详情 | 看图、读来源、加入当前行程 | 以统一地点实体展示媒体、位置、门票、开放状态 | 未核实营业/门票展示为确认事实 |
| 05 | 三方案对比 | 切 A/B/C，比价与强度，选择 | 选择 current draft variant；在同一 Journey 下生成/更新当前日程 | A/B/C 点了仍全部显示 B 的内容 |
| 06 | 每日行程 | 切日期、改时间、替换活动、问 Agent | Agent 仅调整需要改的 slot；地图同步；版本可恢复 | 要求用户重新把地点手动选一遍才能生效 |
| 07 | 出发准备 | 查看待处理、确认出发 | 服务器协调正式计划与执行态；保留待办和状态来源 | 把推荐酒店显示成「已预订」，未核实事实变已确认 |
| 08 | 旅行中 | 看下一站/路线，手动确认到达 | 按真实权限和执行记录持续更新，Guardian 可以主动检查变化 | 根据页面打开就虚构已到达或实时 GPS |
| 09 | Guardian 应变 | 对比替代方案、发起提议 | 发现真实影响时带来源呈现；先作为建议，不直接覆盖共享计划 | 把 demo 异常说成官方新闻；Agent 自动绕过同行权限 |
| 10 | 多人决策 | 参与讨论、本人确认 | 成员绑定确认达到当前决策规则后才正式更新共享版本 | 发起人替别人投票；2/3 却宣称全员同意 |

## 3. 建议的信息与状态架构

```text
CityNexus App
├── Explore Space (01, 02, 03, 04)
├── Journey Space (05, 06, 07, 08, 09, 10)
├── Me (真实产品还需独立设计)
└── Global Agent Layer
    ├── 对话与上下文：journey_id + task_id + authenticated traveler
    ├── 研究工具：地点、来源照片、路线、信息核实
    ├── 可见结果：地图点、地点卡、草案与对比
    ├── 执行工具：活动/导航建议、实时守护
    └── 共同决策：提案、成员意见、版本正式生效
```

**普通人只认一份「我的当前行程」。** Agent 的 draft artifact 与正式 PlanVersion 是后端生命周期，不要让用户重复操作地点才能跨过这条线。浏览器刷新和应用恢复后，仍应回到同一 Journey 与任务成果。

建议旅程生命周期：

```text
新目标 → 自动研究中 → 有可编辑草案 → 已选方案 / 待完善
                        ↓
                  出发准备 → 已启动 → 旅途中 → 已完成
                                   │
                              Guardian 提议
                                   ↓
                             个人/共同决策
                                   ↓
                             正式更新行程
```

Guardian 的提议和协作中的变更是**侧线**，不能直接替换已生效的共享 PlanVersion；未获得必要同意时，原版本仍然使用。

## 4. 这十张图共用的同一份故事数据

- 城市：福建连城；旅行：2026 年 10 月 24 日（周六）至 25 日（周日），两天一晚。
- 三位成员：我、阿杰、小雨；人均预算 **¥500**，不是三人的总预算。
- 默认方案 B：自然轻松，人均预计 **¥470**。A：¥520（超出预算）；C：¥495。
- 住宿：仅推荐，**尚未预订**；部分门票和营业资料待进一步核实，路线时间为估算。
- 在途到达：由本人确认，页面不宣称具备可信 GPS 到场证明。
- Guardian 事件：**明确标注的模拟景区暂停开放**。替代 A：培田古村，人均预计仍 ¥470；替代 B：天一温泉，人均预计 ¥550（超预算）。
- 共享提案：只有「我、阿杰」同意，小雨待确认，即 **2/3**；约定要求三位确认后才可更新正式共享计划。展示为未生效。

## 5. 全局 UI 行为约束

1. 固定底部聊天栏不可遮挡重要按钮或行程卡；键盘弹起时对话框仍能使用。
2. 地图、照片、列表与时间轴共享 source candidate ID；同一地点只提供一份统一的营业、费用、地理来源状态。
3. 只把主动研究、草案编辑、正式出发、付款/预订等不同操作区分到用户真正需要决定的层级；不要把每次普通查询都弹成阻断提示。
4. Agent 的研究步骤可以展示「正在做什么」，但进度必须来自真实任务事件；不能用固定动画当真实工具调用。
5. 任何外部事实都标注已核实/估算/待核实/来源时间；地图示意线必须与可导航的路网计算区分。
6. 多人场景不能让一个成员替其他成员确认；正式生效按既定 server-side authority 规则执行。
7. 单城市研究失败时 Agent 尝试其他已有授权来源，展示当前已有成果而不是整页罢工。
8. 首屏按旅行状态调整：无 Journey 优先输入；DRAFT 优先方案及 Agent 成果；ACTIVE 优先下一站和事件。
9. 优先验证真人操作任务：给一句目标 → 看见地点照片/地图 → 三方案 → 同任务改下午 → 进入正式计划 → 出发 → Guardian 变更经共同确认生效。

## 6. 开发分工参考

- **Codex / Revolution 产品线**：三个一级空间、唯一 Agent 输入与任务上下文、草案-正式行程的桥接、地点/地图/日程同源呈现、手机真机体验。
- **Qoder / 主产品能力线**：真实来源媒体、路线/营业信息读取、Signed Journey/候选映射、Guardian 与多人决策读写契约，接入现有真实服务而不是制造替身。
- **验收**：前后端代码/自动化测试是必要条件，但不等于用户验收。最终要用实际浏览器或手机完成整条旅行链路，关键步骤提供可追溯的真实运行证据。

## 7. 素材限制

这套图面向**布局、架构、按钮位置与产品语义**，不是产品广告文案、真实路况、真实天气、商业定价、景区营业确认或有效订购证明。用于开发时请替换为真实、可授权的媒体与服务端数据。
