3. WHY A ROW IS 292 PX TALL -- the part the grouping question surfaced

   Measured on the live DOM, both languages, at 390x844:
     nav row height            292 px
     the <svg> inside it       (243, 243) (computed width/height), viewBox=0 0 24 24, has a width attribute: False
     rows reachable above the 768 line  2 of 14
     does `#v8-nav-drawer > button svg` match a real row?  NO

   styles.css:332 carries `#v8-nav-drawer > button svg { width: 17px; height: 17px }`, but every
   button is wrapped in a <div> -- the group heading is rendered inside the same wrapper
   (frontend/src/app/V8Experience.tsx:1974 renders `<div>{heading?}{button}</div>`) -- so the child
   combinator never matches, the icon keeps the replaced-element default size, and each of the 14
   rows costs ~292 px instead of ~45 px. The overflow is mostly an icon, not the number of entries.

4. THE PROBE: one selector, nothing else

   Probe scope: a style rule added to the live DOM of this browser session only
   (`#v8-nav-drawer button svg { width: 17px; height: 17px }`). No file under frontend/src was modified to get these numbers.

     arm      scroll_height   overflow_px   row_height   rows above 768   svg
     zh-CN    4512 -> 1054          3668 -> 210         292 -> 45         2 -> 10             (243, 243) -> (17, 17)
     en       4512 -> 1054          3668 -> 210         292 -> 45         2 -> 10             (243, 243) -> (17, 17)

   zh and en come out identical in every pixel column, so the two arms are the same 档 -- the row
   height is driven by the icon, not by the label length. Labels differ (see the receipts).

5. PROPOSAL (for the commander to accept or reject; nothing is implemented here)

   P1  Change the selector's combinator, not the navigation: `#v8-nav-drawer > button svg` ->
       `#v8-nav-drawer button svg` (styles.css:332, one line). Measured effect: overflow
       3668 px -> 210 px, reachable rows 2 -> 10, drags 5 -> 1. Cheapest and it fixes the cause.
   P2  If the product still wants collapsible groups, do it AFTER P1 and treat this file's section 2
       as the budget: after P1 the whole list is 1054 px tall against a 844 px viewport, so collapse
       stops being a reachability requirement and becomes a preference.
   P3  A structural note for whoever implements P1 or P2: the heading lives INSIDE the first row's
       wrapper, so any 'hide this group' control either hides the group label too or needs the
       heading moved out of the wrapper. That is why section 2 subtracts (advance - heading_h)
       per row rather than the whole wrapper height.
   P4  Not proposed: shrinking labels, scrolling to the active row, or a second bottom band. None
       of them addresses a 243 px icon, and ORD-0406 already owns the 76 px band at the bottom.

6. WHAT IS NOT MEASURED HERE

   * Real thumb behaviour. This lane reproduces the commander's finding that CDP touch gestures do
   not emit touchmove on this machine, so 'can a finger drag this list' is still only answerable on
   a real phone (ORD-0400). Every number above is a wheel/DOM measurement.
   * The 210 px that remains after P1: 10 of 14 rows are reachable above the 768 line, so one drag is still
     needed for the last 4 entries. P1 does not claim otherwise.
   * Desktop sidebar geometry (the same routes outside the drawer) -- out of scope for this order.
