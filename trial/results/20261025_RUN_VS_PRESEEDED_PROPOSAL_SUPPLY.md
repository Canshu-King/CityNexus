# 课堂预置提案与 SimulationRun 守护：现读事实与三条处置

目的：把「课堂库预置的那张调整卡」和「开演后守护再生成一张」之间的关系量清楚，供号令者裁课堂口径。本文只给读数与影响面，不裁。

## 怎么量的

课堂演示库复制成临时库（`D:/moodle/_codex_probe_1025/probe9_1025.db`，只读复制，课堂栈未动），在隔离后端上：发票 → 开演 → 注入一次闭馆 → 按「交给守护助手」→ 同时读库。

复跑：`trial/human_walk/_classroom_preseed_vs_run_r1.py`（自带起栈与发票，凭据只在子进程环境）。原始读数：`trial/results/20261022_v3_human_chrome/classroom-preseed-vs-run-1.txt`。

## 读数

1. 开演前库里只有一张提案：预置那张 `89f1f65a…`，状态 PRESENTED，触发事件是课堂库里的闭馆事件 `880cec4e…`，底稿是当前生效方案 `e74a5edb…`（`classroom-preseed-vs-run-1.txt:3`）。
2. 开演 201，注入闭馆 200，run 变「等待守护决策」（`:5`、`:6`）。
3. 守护请求**走了 221 秒**才回来，状态变「等待接受调整」（`:8`）。客户端等 120 秒就先超时了，所以屏上会看到按钮一直转；同一时刻从库里读到的是 GUARDIAN_RUNNING（`:7`）。
4. 守护完成后库里是**两张都 PRESENTED**：预置 `89f1f65a…` 与守护新生成的 `3cdeb15f…`，触发事件与底稿都一样（都挂 `880cec4e…`、都基于 `e74a5edb…`），区别只是 proposed 版本与 source_agent_run_id（`:8`）。
5. run 注入的场景事件在 run 状态里是另一个 id，但守护生成的提案仍挂在课堂库原事件上（`:7` 的匹配读数为 false、`:8` 的 trigger 相同）。

## 屏上会发生什么

行程守护面板取列表里**第一张 PRESENTED**（`frontend/src/trial/mobile/GuardianRealityPanel.tsx:241`），而列表按创建时间升序（`backend/app/main.py:25389`）。因此守护跑完后，老师在屏上看到的仍是**预置那张**，不会是守护新生成的那张。

也就是说：课堂上按「交给守护助手」的可见效果只有「等几分钟、状态换成等待接受」，卡片本身不会换；新卡留在库里，屏上不出现。

## 三条处置与影响面

- **甲：课堂不按守护**（现状推荐）。预置卡秒级可用，主链不动；控制台的慢提示已按实测改成「接上模型时实测要四分钟左右；没接模型会一直停在等待」（`frontend/src/trial/mobile/ClassroomPresenterPanel.tsx:198`），运行手册也已写明课堂上不要按这一键（`trial/results/20261025_CLASSROOM_DEMO_RUNBOOK.md:61`）。代价：真守护能力在课堂里不可见，只能课后演示。
- **乙：开演时不预置提案**。屏上只剩守护卡，但老师要等 221 秒起步，超出三到五分钟预算；且工程上要改启动器与演示库准备，属数据工程，不合课堂主线。
- **丙：守护生成新卡时把同事件的旧 PRESENTED 卡作废**（或列表改取最新）。屏上只留一张、且是最新的，但这是后端口径（旧卡状态机、列表排序都归他人域），且课堂会变成「按了守护就得等」。需要后端口径裁语后才能动。

## 边界

- 这次没有接真模型，守护仍产出提案（走的是服务端规则引擎那条腿）；真模型路径的耗时此前量到 246–252 秒（`guardian-model-walk-1.txt:5`），与这次的 221 秒同量级。
- 两张提案都还没被接受或拒绝，所以「接受一张后另一张会不会失效」没有量；按底稿相同这一点推断会撞底稿校验，但未经实测，不写成结论。
- 时间、位置、闭馆仍是模拟事实；本文只谈提案与守护的服务端行为，不改变这一点。
