## Why this is Revolution, not another ACL paperwork pass
R74 finally lets ordinary collaborators explicitly co-plan a stop, but the happy path still starts with the Journey OWNER discovering the Place. In actual travel, *any* companion can find something remarkable. CityNexus must let B (ordinary collaborator) discover a real public Place, invite A, and explicitly ask: “Can we make this part of everyone's Journey?” A (authorized OWNER and accepted invitation recipient) can sponsor that exact proposal while B retains authorship and agency. C, who was never on the original micro-adventure invitation, must not see B's disclosed Place without **B's deliberate full-Journey sharing choice**, and must never be silently conscripted into group planning.

### R75 user-visible story
1. B discovers a catalog/OSM Place in the running Journey using the existing R66/R67 scout and R63/R64 private side stop. B sends a normal R70 invitation to A only; A accepts independently, as in R70/R71.
2. On B's accepted-source invitation card, B sees **“Suggest this Place for our whole Journey”**, with the *exact names of current Journey members who would be told*, what public Place information would be shared, and the fact that a later shared-plan change still needs separate explicit votes. No background GPS or transfer of private origin/history. B explicitly consents to extend this public Place disclosure from A to the full current Journey set.
3. A, already an addressed and accepted participant of B's invitation, sees **“Sponsor B's discovery as a shared stop”** in the existing Journey UI. A uses the existing R73 proposal action and R74 one-stop grant offers. B and C accept narrowly scoped co-planning grants under their own signed identities and independently vote on the grounded candidate diff.
4. If all current required members authorize and plan feasibility is grounded, A applies one successor PlanVersion via existing authoritative replan acceptance. It now contains B's Place once, without rewriting B's private side quest into shared execution or claiming the group physically arrived.
5. If C declines, B withdraws full-Journey Place sharing before actual publication, provider routes are UNKNOWN, the current plan/cursor changes, or an existing C4 commitment would be violated: **no plan mutation** and useful next-step explanations.

## Security/consent blocker discovered during R74 code review — close before calling R75 complete
In current `backend/app/main.py`, `_offer_shared_stop_coplanning_grant` checks the caller's `MEMBER_MANAGE` capability and that the invitation belongs to the Journey, but does **not** require caller = R70 inviter or separately prove inviter's permission to disclose the Place to all. Therefore a different Journey manager with a known invitation id can offer grant to an uninvited C, and the `invitation_projection(...).co_planning_grants` viewer path exposes the public Place *before* inviter consent to that new audience. This is a real authorization/disclosure edge, not a reason to weaken the ACL.

**Implement the boundary in the server write path**: Until an authenticated, canonical, fresh source-disclosure receipt exists, reject any manager/grant/sponsorship attempt that broadens an R70 invitation's Place audience. The R70 inviter B must author that disclosure with their own signed member principal. Do not assume public catalog data == consent to expose the sender's current interests/whereabouts to the team. Explicitly gate projection so C cannot learn which Place B discovered until B authorized whole-Journey disclosure. Invited A still sees what B previously consented to show A.

Do not let a bare UUID, `invited_by`, possession of an existing grant, or MEMBER_MANAGE alone serve as B's disclosure consent. Do not let a route `GET` silently upgrade disclosure; it must remain read-only.
